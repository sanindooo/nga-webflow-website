# Finsweet CMS Filter v1 double flash when going back to "all"

## Problem

On the Works page, clearing a filter back to "all" flashed twice: the list faded out and in, then tiles showed blank and their images popped in. It took two separate causes and two fixes; the second only showed on phones.

## Symptoms

- Desktop and mobile: blank tiles for a moment after the list fades back in on "all".
- Mobile only, after the image fix: radio picks and "all" clicks still looked like a double flash. Moving the date or area slider back to its ends re-showed exactly the same projects without any glitch.

## What Didn't Work

- **Blaming Finsweet for rendering twice.** Measured with a `renderitems` listener and `document.getAnimations()`: one render and one fade-out plus fade-in per click. Finsweet runs once.
- **Coalescing ScrollTrigger refreshes.** Each filter change fired three `ScrollTrigger.refresh` calls (one per list instance plus a backup MutationObserver) and one more per image load (28 on a fresh page). Batching them (`filterActiveState.ts`, one refresh per frame, image loads debounced by `IMAGE_SETTLE_MS`) was worth keeping, but did not remove the flash.
- **Holding the list until images decode, on its own.** `revealAfterDecode` (`src/utils/worksFilter.ts:205`) keeps the visible list at opacity 0 until the first six tiles decode. With Finsweet's own fade still running, the user described it as "the flash is trying to flash, but it's being held": still glitchy.

## Solution

1. **Small images for the listing tiles.** CMS images imported through the API have no srcset, so every tile loaded the 2560 to 4000px hero (1 to 4MB). Finsweet removes filtered-out items from the DOM, the browser drops their decoded bitmaps, and on "all" they decode again in 200 to 500ms, well after Finsweet's 100ms fade-in. A `Thumbnail` image field (1600px WebP, ~100 to 290KB) now feeds the grid tile, generated by `scripts/api/webflow/create-works-thumbnails.mjs`. This fixed desktop.
2. **Turn off Finsweet's fade and fade in once ourselves.** Set on both list wrappers (grid and row view):

   ```html
   <div fs-cmsfilter-element="list" fs-cmsfilter-duration="0" ...>
   ```

   Finsweet then swaps items instantly. `revealAfterDecode` supplies the only transition: opacity 0, wait for the leading images to decode (`DECODE_TIMEOUT_MS` cap, 700ms), then a single 200ms fade-in. This fixed mobile (released in v1.1.19 plus the attribute).

## Why This Works

Finsweet's default animation is a fade-out, swap, fade-in: two visible opacity changes. On mobile the open filter panel is a 50vh overlay above the grid. Sliders keep the panel open, so most of that transition happens behind it. Radio and "all" clicks close the panel instantly (`filterPanels.ts`), exposing the full out-and-in on a grid whose content changes heavily. That reads as a double flash. With `fs-cmsfilter-duration="0"` there is one transition, and it starts only once the tiles can paint.

## Prevention

- Start any Finsweet v1 list that sits under an overlay or sticky filter UI with `fs-cmsfilter-duration="0"` and do one fade-in yourself.
- Never bind full-size CMS images to listing tiles. API-imported images get no srcset; use a dedicated thumbnail field.
- When filtering "looks broken" while testing in a hidden or background browser tab, check `document.visibilityState`. Hidden tabs pause Web Animations, so Finsweet's `renderingQueue` promise never resolves and the list never re-renders. Finish animations (`document.getAnimations().forEach(a => a.finish())`) or test in a visible tab.
- Two DOM traps when hooking `renderitems`: Finsweet still has the list at `display: none` when the event fires, so nothing can be measured; and `offsetParent` is `null` for everything inside ScrollSmoother's fixed wrapper, so use `getClientRects().length` to test visibility.
